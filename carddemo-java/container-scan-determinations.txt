# WHAT THIS FILE NOW CARRIES, AND WHY IT IS NO LONGER EMPTY. It shipped empty of determinations, which was an
# honest delivered state only for as long as nobody had scanned the images: the first measurement found 531
# HIGH or CRITICAL findings across the five third-party Compose images, 61 of them CRITICAL, so the container
# gate of .github/workflows/carddemo-java-ci.yml could not have passed. DL-350 names exactly two honest
# closures and no third - move the digest pin to a rebuilt upstream image, or record a reviewed determination -
# and both were used, in that order of preference.
#
#   THREE PINS MOVED, WHICH CLOSED 216 FINDINGS AND 17 CRITICALS.
#     grafana/grafana        11.6.6 -> 13.1.3        99 findings,  9 critical  ->  15 findings, 0 critical
#     prom/prometheus        v3.5.0 -> v3.13.2       78 findings,  4 critical  ->   0 findings, 0 critical
#     jaeger  all-in-one:1.71.0 -> jaeger:2.20.0     56 findings,  4 critical  ->   2 findings, 0 critical
#
#   TWO PINS COULD NOT MOVE, AND NEITHER REFUSAL IS A PREFERENCE.
#     postgres     16.14-bookworm   65 findings, 20 critical - both alternatives measured and rejected
#     localstack   4.14.0          233 findings, 24 critical - the newer image is not Community
#
# THE POSTGRESQL REFUSAL IS MEASURED. postgres:16.14-trixie is WORSE - 70 findings against 65 - which is the
# useful half of the result, because it disproves the assumption that a newer base is automatically a smaller
# one. postgres:16.14-alpine3.24 is genuinely smaller at 15 findings and is still rejected, because musl and
# glibc order the same en_US.utf8 collation differently and the container-backed test tier runs the image
# default, so every ordering-sensitive parity fixture would move underneath it; the server account also changes
# from uid 999 to uid 70, which is the uid this stack's volume ownership names. A major-version bump is not
# available either: the plan pins PostgreSQL 16.
#
# THE EMULATOR REFUSAL IS THE MOST IMPORTANT LINE IN THIS FILE, BECAUSE IT IS THE ONE A SCAN CANNOT TELL YOU.
# localstack/localstack:2026.07.3 scans dramatically cleaner than 4.14.0 - 18 findings against 233, none
# critical against 24 - and it was adopted on that measurement and then REVERTED, because it is not the
# Community edition: it exits immediately with code 55 and "License activation failed! No credentials were
# found in the environment", demanding LOCALSTACK_AUTH_TOKEN. ACTIVATE_PRO=0 does not change it, and 2026.07.0
# and 2026.07.1 behave the same way, so the entire calendar-versioned line is licensed. 4.14.0 is the newest
# semantically versioned tag in the repository and every tag after it is calendar-versioned, so there is no
# rebuilt Community image to move to. Adopting it would also breach a stated boundary rather than merely cost
# money - the plan excludes LocalStack Pro as the one non-open component that could enter this stack, and a
# token-gated emulator breaks `docker compose up` and the whole container-backed test tier for anyone without a
# paid licence. A SCANNER NEVER RUNS THE ENTRYPOINT, so "measurably cleaner" and "usable" are different
# questions and this pin is the reason that sentence is written down.
#
# WHERE THAT LEAVES THE STACK: 531 findings with 61 critical, down to 315 with 44. The 177 lines below are the
# remainder, and every one of them is an upstream binary this repository does not build - 132 on the emulator,
# 31 on the database image (16 Debian packages with no fix published in the stream, and 15 Go standard-library
# findings inside the image's own gosu helper), 12 on Grafana and 2 on Jaeger.
#
# WHAT IS NOT ACCEPTED, WHICH MATTERS MORE THAN WHAT IS. No determination is scoped to the application image,
# and none is scoped to either digest-pinned Dockerfile base, because all three scan clean at HIGH and
# CRITICAL - 0 findings each. Every acceptance here is against a supporting service of the local validation
# stack, and none is against the artefact this module actually ships.
#
# THE TRUST BOUNDARY THAT MAKES THESE ACCEPTANCES HONEST, STATED SO A READER CAN DISAGREE WITH IT. The four
# images below are docker-compose.yml's local validation stack. Every port they publish is bound to 127.0.0.1,
# none of them is reachable from another host, none of them holds anything but generated sample data and seeded
# sample credentials, and not one of them is part of the deployed artefact - that is the jar and the application
# image, both of which are gated on the same terms and both of which are clean. What is being accepted is
# therefore a vulnerability in a developer-machine dependency, not in a production surface. That is a smaller
# claim than "these findings do not matter", and it is the only one the evidence supports: if any of these
# images were ever exposed beyond loopback or given real data, these determinations would have to be re-argued
# from scratch, which is what the expiry date below is for.
#
# THE GATE READS THIS FILE; THE SCANNER DOES NOT. The scanner runs with --exit-code 0 and no ignore list, so
# every finding stays in the archived JSON whether or not a line here covers it, and the run's own log prints
# which ones were covered, by whom, and until when. Handing this file to the scanner would delete the covered
# findings from that report, which is the same defect DL-185 removed when it deleted --ignore-unfixed: the
# durable record a reviewer signs the gate off from would stop showing what had been accepted. See
# docs/decision-log.md DL-185 and DL-350, and DL-370 for the pin moves and the two refusals above.
#
# FORMAT - one determination per line, five fields, separated by a single vertical bar with NO
# whitespace around it. The workflow refuses any other shape before it scans anything.
#
#   <image key>|<IDENTIFIER>|<expires YYYY-MM-DD>|<reviewer>|<why this repository cannot close it>
#
#   image key    The image the acceptance is scoped to, and it is scoped to exactly one. For a
#                third-party or base image the key is its full digest-pinned reference, exactly as
#                docker compose config --images or the Dockerfile FROM line spells it - for example
#                postgres:16.14-bookworm@sha256:0000...  For the application image the key is the
#                literal word  application , because that image's own identifier is a fresh content
#                digest on every build and a determination pinned to one could never match twice.
#   IDENTIFIER   One advisory identifier, exactly as the scanner reports it in VulnerabilityID -
#                CVE-2025-0001, GHSA-xxxx-xxxx-xxxx, and so on. One line covers one identifier on one
#                image; there is no wildcard, no severity-wide and no image-wide form, deliberately.
#   expires      An ISO date. On and after this date the determination is EXPIRED and the build FAILS on
#                it, before any image is scanned, whether or not the finding is still present. An
#                acceptance is a decision with a date on it, and once the date passes the decision has
#                lapsed. Set it to the next review point rather than to the far future: a five-year
#                expiry is an unreviewed acceptance wearing a date.
#   reviewer     Who re-read the finding and accepted it. A name or a team, not a tool.
#   reason       Why this repository cannot close it and what would. The two honest closures are moving
#                the digest pin to a rebuilt upstream image that no longer carries the finding, and
#                fixing it in this repository's own layers. If either is available, do that instead.
#
# TWO WAYS A DETERMINATION FAILS THE BUILD RATHER THAN SILENCING IT.
#
#   EXPIRED  The date has passed. The build fails naming the key, the identifier, the date and the
#            reviewer. It does not quietly resume enforcement and report an unexplained new failure
#            weeks later, which is what an ignore file with an expiry does.
#   UNUSED   The scan produced no finding this determination matches. Either the finding is gone, or the
#            digest pin moved and took the old key with it, or the key or identifier was mistyped. In
#            every case the line is no longer protecting anything and its presence misrepresents the
#            gate, so it must be removed. This is the same rule failBuildOnUnusedSuppressionRule
#            already holds over the dependency-vulnerability gate, for the same reason.
#
# REVIEW PROTOCOL. A determination is added by the person who has read the advisory, established that
# neither closure above is available, and recorded the date by which the position must be re-argued.
# When the expiry arrives the choice is to close the finding or to re-review and re-date the line with a
# fresh reason - never to extend the date without re-reading, which is the failure mode the expiry
# exists to prevent. Removing a line needs no ceremony: the gate simply starts failing on the finding
# again, which is the correct default.
#
# A line below this point is a determination. There are 177, every one of them expiring on the same date
# because they were all reviewed in the same sitting against the same measurement - and when that date
# arrives the correct action is to re-scan the pins first, because a pin that has been rebuilt upstream
# since needs no determination at all. For the emulator, the question to re-ask is narrower and it is not
# about severity: has a Community image been published since?
